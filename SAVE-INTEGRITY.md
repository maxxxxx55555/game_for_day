# Offline save integrity

This edition validates saved finances, event-state types, bounds, finite numbers and RNG types before applying game state. Saves use bounded reads, atomic replacement, known-good backups and purpose-bound HMAC-SHA256 with a random per-installation key. Valid older profiles migrate once; protected slots reject unsigned downgrades. A valid authenticated backup replaces a rejected main file. A fresh write with no valid previous snapshot preserves the rejected file in a .rejected copy; no save data is executed.

This detects ordinary save editing and accidental corruption. It is not server-authoritative anti-cheat or unbreakable DRM: a device owner can inspect the key, restore an older full profile or modify the executable. There is no kernel driver, process scanner, account service, telemetry or hidden network dependency. This is an offline single-player game; no claim of perfect security or zero bugs is made.

Back up the entire existing Godot user-data folder, including save_integrity.key and guard_*.lock, while the game is closed. Copying only a protected save to another installation is insufficient. Keep a separate backup before upgrading; migration preserves valid progress but an older executable does not understand the new protection. If a slot is damaged, the loader tries its authenticated known-good backup; a new-life action deliberately clears the current-life checkpoint.

The local key is generated on the player's machine and is never distributed in the source or game archive. Report a reproducible fault with game version, actions and a copy of the affected profile; do not post personal file paths or profile contents publicly.

Cryptographic API: https://docs.godotengine.org/en/4.0/classes/class_crypto.html

Version 1.2.1 additionally checks nested runtime state and reports failed saves. Save protection is unchanged (schema 4 / configuration guard v1), so valid 1.2 profiles retain their keys and progress.

## V2 release boundary

BuildIntegrity runs before model autoloads. tools/build_manifest.py deterministically generates data/critical-manifest.json and a compiled TrustedData snapshot/root from every shipping data JSON and the audio catalog. Export preflight checks that both generated files match reviewed sources; it never silently blesses a modified installation. Startup verifies the manifest against its compiled SHA256 and every data entry. A mismatch logs the affected paths, presents EN/RU feedback and uses immutable trusted fallback content. Save/key creation, backup copies, repair, migration, settings writes and progress deletion are disabled in this safe mode; existing authentic progress remains readable. Only integrity.log may be written. This is corruption/modification detection, not external attestation of the executable.

A rejected protected primary is recovered only from a valid authenticated backup, with a localized message and a bounded local log containing no key or HMAC value. If neither copy is valid, the loader rejects the profile and says so. Unchanged valid save-load-save round trips retain a stable file hash. Purpose domains, install-key bytes and legacy user-data aliases remain unchanged.

Public Windows exports physically exclude private verifier resources. QA requires both a separate compiled custom feature and GAME_QA=1. Release templates omit console wrappers, debugger support and path overrides. Every PCK entry and the directory are encrypted. The build key is supplied only through the environment and a separately compiled matching custom template; neither private keys nor private QA builds belong in public artifacts. A stock engine or the other build key cannot mount the encrypted pack. A device owner can still reverse engineer a native binary or inspect memory; encryption is not DRM and this edition claims no prevention of all possible cheats.

The money ledger uses signed int64 cents with a +/-900,000,000,000,000-cent bound ($9 trillion), below the exact-integer boundary of double precision and above the $250 billion goal. Direct invalid/nonfinite/out-of-bound dollar inputs leave state unchanged. Monetary additions/multiplications are checked before debit or asset mutation. Stock/crypto quantities and stochastic quote ratios are distinct from cash; liquidation credits whole cents, rounded down. Business definitions, costs, passive income, dividends, inheritance and grant postings use cents. Inheritance retains the edition's nearest-whole-dollar rounding. Displayed total wealth is capped at the ledger's upper boundary; sales which would overflow cash are refused without consuming holdings. Business scale is limited to16,384, beyond the campaign target.

FX holdings are integer thousandths, capped at9,000,000,000,000,000 thousandths per currency. Positive sub-cent orders that round to zero are rejected. Foreign acquisition and dollar liquidation round down; same-quote spread cannot create cents. New authenticated saves include exact cent/thousandth fields plus compatibility dollar views, which must agree. Legacy1.4 dollar balances/prices migrate to nearest cent and FX quantities to nearest thousandth; maximum migration quantization is0.005 dollar/0.0005 foreign unit. Old representable normal campaign profiles retain progress. Impossible or out-of-bound legacy states remain rejected rather than overflowing.

Grant eligibility uses saved simulation_ticks/grant_ready_tick/last_grant_tick integers. One half-quarter is one tick; the cooldown is eight ticks. Changing or rolling back the system clock has no effect. An old cooldown migrates from saved calendar progress. Repeated acceptance in the same tick fails before cash, statistics or eligibility changes. Complete-profile rollback by a device owner is outside offline prevention guarantees.

Critical JSON, generated trust source and Python tooling have explicit LF checkout rules in .gitattributes. Fresh Windows checkouts therefore preserve the reviewed trust bytes with core.autocrlf enabled; creator-license byte rules are retained. test_critical_manifest.py rejects a missing checkout policy.

Startup caps the manifest at64KiB and each critical data file at8MiB before reading content; SHA256 uses64KiB streaming chunks. Oversized or unreadable content enters the same read-only safe mode instead of allocating arbitrary input size. Integrity dialogs use this game's own theme and update immediately with a language change.
